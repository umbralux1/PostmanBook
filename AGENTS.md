# AGENTS.md — контекст для агентов

HTTP-тренажёр для специалистов поддержки: теория + встроенный мини-Postman, задания
проверяются автоматически. FastAPI + SQLModel + Alembic, Jinja2 + HTMX + Alpine.js,
Tailwind (собран заранее), SQLite. Владелец пишет по-русски — отвечай по-русски.

- Команды: `make help` (главные: `make install`, `make dev`, `make check`). Python 3.11+.
- Устройство, API, формат YAML, деплой — в `README.md`. Читай его перед изменением
  контента, проверки заданий, языков, комнат или деплоя.

## Решения и почему (не менять без владельца)

**Проверка заданий — по ответу сервера, на фронте (фазы 1 и 2).** Учебный API
детерминирован (echo возвращает то, что получил), поэтому верный запрос даёт верный
ответ. `app/static/js/checker.js` — чистые функции, сверяет ответ с `expected` из YAML
(`response` / `steps` / `ordered` / `require_console`), задание засчитывается через
`POST /api/tasks/{id}/complete`. Сервер задания не проверяет. Вопросы с вариантами
и проверку свободных ответов владелец отклонил.
- Фаза 1 — ответы из мини-Postman. Фаза 2 — ответы из журнала ученика: middleware пишет
  запросы с `X-Student-Id` вместе с ответом (`services/recorder.py`), страница берёт
  журнал (`/api/journal` + SSE) и гоняет через тот же `checker.js` (`static/js/phase2.js`).
  `validator.py` (`expected.request`) — только подсказки в журнале, на зачёт не влияет.
- Фаза 2: два заголовка — `X-Student-Id` (ученик) и `X-Task-Code` (задание); без
  любого из них не засчитывается. Журнал по cookie, не по коду в URL. На странице главы
  фазы 2 мини-Postman нет (решения владельца).
- Каждое задание фаз 1–2 обязано иметь эталонное решение и типичные ошибки в
  `tests/test_content_solutions.py` (`SOLUTIONS`/`MISTAKES`, фаза 2 —
  `PHASE2_SOLUTIONS`/`PHASE2_MISTAKES`): тест гоняет их через настоящий сервер и тот же
  `checker.js` (нужен Node.js).

**Задания — простые и атомарные (решение владельца, с главы 4).** Одно задание — один
запрос и одна проверка ответа (`expected.response`). Сценарий из нескольких шагов —
несколько заданий подряд (следующее может брать токен/id из предыдущего), а не
`steps` / `ordered` в одном задании: многошаговые задания путают ученика и усложняют
проверку. `steps` / `ordered` в `checker.js` остаются ради старых заданий главы 3.

**Адреса в контенте — `{{BASE_URL}}/api/...`**, сервер подставляет адрес сайта из
запроса (`services/localize.py`). Хост нигде не хардкодить. За HTTPS-прокси нужен
uvicorn с `--proxy-headers --forwarded-allow-ips='*'` (есть в `docker/start.sh`),
иначе в заданиях будет `http://` и мини-Postman не отправит запрос.

**Языки.** `SOURCE_LANG = "ru"`: строки в коде — русские ключи каталога, основные
YAML — русские. `DEFAULT_LANG = "en"`: язык для пользователя по умолчанию.
- Строки: шаблоны `{{ _("…") }}`, JS/Alpine `t("…")`, Python `ApiError(...)` / `N_("…")`;
  перевод — `app/locales/en.json`. `tests/test_i18n.py` падает на непереведённых и
  лишних ключах (`make i18n-missing`).
- Контент: `*.en.yaml` рядом с оригиналом; `expected` обязан совпадать с оригиналом,
  кроме текстов `hint`/`console_hint` (проверяет загрузчик и `make content-check`).
- Подписи интерфейса Postman (Params, Headers, Send, Pretty, Test Results…) — на
  английском в обоих языках, как в настоящем Postman.

**Комнаты (совместная работа).** WebSocket `/ws/rooms/{code}`, хаб в памяти
(`services/room_hub.py`), фронт `static/js/collab.js`. Мини-Postman (фаза 1) в комнате общий,
задание засчитывается всем онлайн. В фазе 2 журнал, выбор задания и зачёт личные.
- Поля общего состояния перечислены дважды и должны совпадать: `SHARED_FIELDS` в
  `static/js/builder.js` и в `services/room_hub.py`.
- Курсоры и выделения адресуются путём по индексам DOM от `<body>`, поэтому DOM
  страницы должен быть одинаковым у всех участников: условия, зависящие от
  пользователя, — через `x-show`, а не `x-if` / `{% if %}`.
- Многопользовательские тесты — на живом uvicorn (фикстура `live` в
  `tests/test_rooms.py`): `TestClient` даёт каждому WebSocket свой event loop, и
  рассылки между участниками в нём ненадёжны.

**База — только SQLite** (решение владельца). WAL, папка создаётся сама. В Docker —
`/srv/data/trainer.db`; `docker/start.sh` стартует от root, отдаёт папку пользователю
`trainer` и понижает права (тома и диски монтируются с владельцем root). Один процесс
uvicorn: SQLite, комнаты, SSE и rate limit живут в одном процессе.

**Деплой — Render**, Blueprint `render.yaml`, деплоит ветку `main`
(`origin` = github.com/umbralux1/PostmanBook). Бесплатный план: файл базы стирается при
деплое, перезапуске и засыпании; постоянный диск (`/srv/data`) — только на платном плане.
Это устраивает владельца: тренажёр нужен примерно на месяц, потеря прогресса при
перезапуске допустима. Постоянный диск, внешнюю базу и другие способы сохранить данные
на Render не предлагать.

## Ловушки

- Alpine: в массиве `:class` пиши `cond ? 'x' : ''` — `cond && 'x'` добавляет класс `false`.
- Статику в шаблонах подключай через `static_url('js/…')` (`pages.py`, добавляет
  `?v=<mtime>`), не `url_for('static', …)`: иначе браузер (особенно Safari) держит
  старый `checker.js` в кэше, и задания с новыми проверками не засчитываются.
- Новые Tailwind-классы в шаблонах → `make css` (CSS собран заранее). Стили
  мини-Postman — классы `pm-*` в `static/css/app.css`.
- Контент грузится в БД при старте; `make dev` перезапускается при правке
  `.yaml`/`.json`, иначе — `make content-sync`. Синхронизация удаляет из БД главы
  и задания, которых нет в YAML (попытки остаются), поэтому `id` заданий не менять:
  прогресс привязан к `id`.
- Учебный набор тикетов (`services/ticket_seed.py`) фиксирован: на порядок и названия
  опираются задания главы 3 («SMS code not received» на 2-й странице при `limit=10`).
  Тексты на английском (решение владельца), одни для RU/EN (`expected` общий). Лимит `/api/limited` — в
  памяти процесса; в тестах его сбрасывает фикстура `engine`.
- Миграции: `make migration MSG="…"`; у внешних ключей задавай имена (SQLite, batch-режим).
  При старте миграции применяются сами, в том числе к старым базам без `alembic_version`.
  Batch-режим пересоздаёт таблицу, поэтому `alembic/env.py` на время миграций SQLite
  выключает `foreign_keys` (иначе таблица с данными, на которую ссылаются, — `user` ←
  `attempt` — не удаляется) и после проверяет `foreign_key_check`. Миграции с данными
  проверяй на базе с пользователями (`tests/test_migrations.py`), не только на пустой.

## Работа с владельцем

- Коммит — только по просьбе, на `main`, с подписью Co-Authored-By. Пушит владелец
  со своего Mac (у агента нет его учётных данных GitHub).
- В каждом коммите — обновлённая дока: `README.md`, `AGENTS.md` и другие места, где
  описано изменённое поведение. Если доку менять не нужно, проверь это перед коммитом.
- `HANDOFF.md` в корне (игнорируется git) — временная передача контекста следующему
  агенту: текущая задача, что сделано, что осталось, открытые вопросы, незапушенные
  коммиты. Прочитай его в начале работы, обновляй после каждого коммита и при смене
  задачи. Устойчивые решения переноси в `AGENTS.md`/`README.md`, а не копи в handoff.
- Перед правками проверяй `git status`: владелец может менять файлы сам.
- `_to_delete/` (игнорируется git) — временные архивы агентов, можно удалять.

## Идеи для мини-Postman (предложены, не начаты)

Ближе к настоящему Postman; делать только по решению владельца.
- Вкладка Authorization: Bearer token сам подставляет заголовок `Authorization`.
- Body: form-data и x-www-form-urlencoded, а не только raw JSON.
- Переменные окружения (`{{base_url}}` и свои) — как в Postman Environments.
- History: список отправленных запросов, повтор в новой вкладке.
- Сохранение вкладок запросов в localStorage: сейчас после перезагрузки страницы
  остаётся одна вкладка по умолчанию.
