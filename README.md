# HTTP-тренажёр

Веб-тренажёр для специалистов поддержки: учимся делать HTTP-запросы, читать
статус-коды, заголовки и тело, а потом переносим навыки в настоящий Postman.
Это безопасная песочница: без реальных токенов и без production.

**Этап 1 (готово):** фаза 1, то есть встроенный мини-Postman, учебный API, автоматическая
проверка заданий, прогресс, чек-лист и тест главы. Контент: глава 1 «Первый запрос»
(HTTP-запрос, URL, мини-Postman, сломанные адреса, мини-тикет; 5 заданий) и глава 2
«Ответ сервера» (статус-коды, типы JSON, заголовки, токены, Console, два мини-тикета;
9 заданий).
**Фаза 2 (готово):** глава 3 «Методы HTTP и статус-коды в диагностике» — запросы из
настоящего Postman к учебному API (тикеты, 409, 422, пагинация, 429, 503 и `X-Request-ID`;
10 заданий), на странице главы — панель «Твой Postman» с живым журналом запросов.
Главы 4–7 из плана курса — пока анонсы: название, цель, время и список тем, без
теории и заданий.
**Задел:** API фазы 3 (вставка ответа внешнего API) работает и покрыт тестами,
для неё остаётся сделать UI и контент.
**План курса** (7 глав, фазы, приоритеты, нужные доработки учебного API) —
[`content_source/COURSE_PLAN.md`](content_source/COURSE_PLAN.md).

## Быстрый старт

### Docker (рекомендуется)

```bash
cp .env.example .env        # необязательно
docker compose up --build
```

Откройте http://localhost:8000. База — файл SQLite в томе Docker `trainer-data`, он
переживает пересборку и перезапуск контейнера. Миграции (Alembic) применяются при
старте, контент загружается из YAML.

### Локально (SQLite)

Нужен Python 3.11+.

```bash
python3.12 -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"
uvicorn app.main:app --reload
```

По умолчанию создаётся `trainer.db` (SQLite). Миграции Alembic применяются при старте
автоматически, в том числе к старой базе, созданной до появления миграций.

### Проверки качества

```bash
pytest                 # тесты (in-memory SQLite, без моков)
node --test tests/js/*.test.cjs   # unit-тесты проверки ответов (нужен Node.js 18+)
ruff check . && ruff format --check .
mypy app               # strict
pre-commit install     # хуки: ruff, mypy, проверка YAML-контента
python -m app.cli check-content
```

  services/

    hints.py         подсказки validator.py с подстановкой {{param}} (без eval), RU/EN
    rooms.py         комнаты: личная комната, приглашение, имя и цвет участника
    room_hub.py      WebSocket-хаб: присутствие, ретрансляция, общее состояние
    recorder.py      журнал фазы 2: запрос ученика (X-Student-Id) + ответ → ReceivedRequest
    students.py      личный код ученика (User.student_code) из заголовка X-Student-Id

    sse.py           брокер событий для SSE (личный канал ученика)
  pages.py           HTML-страницы (Jinja2 + HTMX + Alpine.js)
  content/           главы и задания (YAML/Markdown)
  templates/, static/
  static/js/checker.js  проверка задания по ответу сервера, фазы 1–2 (чистые функции)
  static/js/task_order.js  какое задание выбрать при открытии главы и после засчитанного
  static/js/task_store.js  Alpine.store("task"): выбранное задание, автопереход; чек-лист
  static/js/builder.js     мини-Postman (только страницы фазы 1)
  static/js/phase2.js      панель «Твой Postman» (страницы фазы 2): журнал, проверка

**Выбор задания.** При открытии главы мини-Postman сразу решает первое невыполненное
задание (по `order`) и его условие раскрыто; если всё сделано — «Свободный режим».
Когда задание засчитано, через 2 секунды (успеть увидеть «Task complete!») мини-Postman
переходит к следующему невыполненному после него, раскрывает его карточку и
прокручивает к ней; дальше по порядку всё сделано — остаётся на текущем. Если за паузу
выбрали другое задание, переход отменяется. Логика — `static/js/task_order.js`
(чистые функции, `make test-js`) и `Alpine.store("task")` в `builder.js`
(`openFirst`, `advanceFrom`). В комнате переход делает тот, кто засчитал задание, и он
расходится всем как `taskId`; выбор при открытии главы не рассылается — задание,
уже выбранное в комнате, приходит в `welcome` и заменяет его.

**Вкладки запросов.** Как в Postman: «+» открывает новую пустую вкладку, «✕» (или
средняя кнопка мыши) закрывает. У каждой вкладки свои метод, адрес, параметры,
заголовки, тело и ответ; Console, история ответов для проверки и выбранное задание
общие. Вкладок не больше 10, при закрытии последней открывается пустая. Логика —
`static/js/builder.js` (`TAB_FIELDS`, `addTab`/`closeTab`/`selectTab`).

**Console.** Как в Postman, это не вкладка запроса, а журнал последних 10 запросов:
кнопка **Console** в нижней строке мини-Postman открывает и закрывает панель под
ответом (`consoleOpen`, `toggleConsole()` в `builder.js`). Для `require_console`
открытие засчитывается, если Console открыли после правильного ответа или ответ
пришёл, пока она открыта.

**Своя прокрутка.** На широком экране (от 1024px, `lg:`) колонка мини-Postman
(`#builder` в `chapter.html`) не выше окна и прокручивается сама, не двигая теорию;
на телефоне она идёт под теорией и прокручивается вместе со страницей.

**Как проверяется задание в мини-Postman.** Задание считается выполненным, когда
сервер вернул правильный **ответ**. Учебный API детерминирован: echo возвращает
ровно то, что получил, `/api/status/404` всегда отвечает 404. Поэтому правильный
запрос всегда даёт один и тот же ответ, а неправильный — другой.

Ожидания к ответу описаны в YAML задания. После каждого Send функция
`static/js/checker.js` сверяет с ними ответ и показывает подсказку у первого
несовпадения. Это чистые функции без DOM и сети, они покрыты unit-тестами
(`make test-js`). Когда задание выполнено, фронт вызывает
`POST /api/tasks/{id}/complete`, и сервер сохраняет прогресс.

`tests/test_content_solutions.py` проверяет сам контент: отправляет на настоящий
сервер эталонное решение и типичные ошибки для каждого задания и прогоняет ответы
через тот же `checker.js`. Решение должно засчитываться, ошибки — нет, с нужной
подсказкой. Тест берёт задания фаз 1–2 из всех глав (`app/content/tasks/*.yaml`)
и падает, если у какого-то задания нет решения в `SOLUTIONS` (фаза 1) или
`PHASE2_SOLUTIONS` (фаза 2). Добавили задание — добавьте туда его решение.

Мини-Postman добавляет к запросам заголовок `X-Task-Code` (в Headers он с замком).
Для фазы 1 сервер его только логирует (и echo возвращает в `task_code`); в фазе 2 он
ни на что не влияет.

**Фаза 2: настоящий Postman.** На странице главы с `phase: 2` мини-Postman нет
(`#builder` и `builder.js` не подключаются): сайт не отправляет запросы, только
показывает, что получил сервер. Справа — панель **«Твой Postman»**
(`components/postman_panel.html`, `static/js/phase2.js`): личный код с кнопкой
«Скопировать», какое задание выбрано, результат проверки (Test Results) и
журнал запросов (метод, путь, статус; в раскрытой записи — заголовки запроса, заголовки
и тело ответа).

- Ученик шлёт запросы с одним заголовком `X-Student-Id` (личный код,
  `User.student_code`). Задание выбирается на странице, как в фазе 1: кнопкой «Решать»
  или автопереходом. `task_store.js` сообщает выбор серверу — `PUT /api/journal/task`
  `{"task_id": …}` (только задания фазы 2) → `User.phase2_task`; запросы ученика
  помечаются заданием, выбранным в момент отправки. При автопереходе сервер
  переключается на следующее задание сразу, карточка — через 2 с (запрос, отправленный
  в эту паузу, засчитывается уже следующему заданию).
- Middleware (`main.py` → `services/recorder.py`) записывает запрос к `/api/*` (кроме
  служебных `/api/tasks`, `/api/journal`, `/api/room`, `/api/me`, `/api/progress`) с
  `X-Student-Id` известного ученика в `received_requests` **вместе с ответом**
  (`response_status`, `response_headers`, `response_body`). Без `X-Student-Id` или с
  неизвестным кодом запрос обрабатывается как обычно, но не записывается. Если задание
  не выбрано, запрос записывается с пустым `task_code` — в журнале подсказка выбрать
  задание.
- Журнал личный, ученик определяется по cookie сайта (не по коду в URL):
  `GET /api/journal` — запросы за последние 30 минут (до 100), `GET /api/journal/stream` —
  SSE, событие `request` с новой записью. Брокер — в памяти процесса (`services/sse.py`).
- Проверка — тем же `checker.js` и тем же форматом `expected`, что в фазе 1:
  история задания = ответы на запросы, помеченные этим заданием (старые → новые). При открытии
  страницы проверяются все задания главы по журналу (засчитается и запрос, отправленный
  до открытия вкладки). Засчитанное — `POST /api/tasks/{id}/complete`, только себе.
  Автопереход — как в фазе 1.
- Если у задания есть `expected.request`, запрос дополнительно сравнивается с эталоном
  (`validator.py`), и подсказки «что не так в запросе» показываются в журнале на
  языке ученика. На засчитывание это не влияет.
- Комнаты: в фазе 2 у каждого свой Postman — выбор задания не рассылается в комнату,
  журнал и засчитывание личные; комната показывает присутствие, курсоры и выделения.

### Учебный API

| Метод и путь | Что делает |
|---|---|
| `GET/POST/PUT/PATCH/DELETE /api/echo` | Возвращает `method`, `path`, `args`, `headers`, `json`, `data`, `task_code`. Если JSON невалиден (при `Content-Type: application/json`), отвечает `400 invalid_json` |
| `GET /api/status/{code}` | Отвечает этим кодом. Разрешены только 200, 201, 204, 301, 302, 400, 401, 403, 404, 409, 422, 429, 500, 502, 503 |
| `GET /api/status/500`, `502`, `503` | В теле, кроме `status`, — `request_id` (тот же, что в заголовке `X-Request-ID`) |
| `GET/POST /api/tickets`, `GET/PUT/PATCH/DELETE /api/tickets/{id}` | CRUD заявок. Возможные ошибки: 415, 400, 422, 404, 409 |
| `GET /api/tickets?status=&page=&limit=` | Список: `{items, page, limit, total, pages, count}`; `page` с 1, `limit` 1..100 (по умолчанию 10), `count` — сколько на этой странице |
| `POST /api/tickets/reset` | Вернуть тикеты ученика к учебному набору (нужен `X-Student-Id`, иначе `400 student_required`) |
| `GET /api/limited` | Учебный лимит: 3 запроса за 10 с на ученика (`X-Student-Id`, без него — на IP). Дальше `429 rate_limited` + `Retry-After: N`; в ответах `X-RateLimit-Limit`/`X-RateLimit-Remaining` |
| `POST /api/auth/login` | Глава 4: `{username, password, expires_in?}` → `{access_token, token_type, expires_in, expires_at, username, role}`. Учётка `agent` / `support123`, `expires_in` 5..3600 с (по умолчанию 900). Ошибки: 401 `invalid_credentials`, 415, 422 |
| `GET /api/auth/me` | «Кто я»: принимает `Authorization: Bearer <токен>`, `Authorization: Basic <base64>` и `X-API-Key`; в ответе `auth` — каким способом вошли (`bearer`/`basic`/`api_key`) |
| `POST /api/auth/api-keys` | Создать API-ключ (`201 {api_key}`), нужна авторизация |
| `POST /api/auth/change-password` | `{old_password, new_password}`: меняет пароль ученика и отзывает все его токены и ключи. Нужны авторизация и `X-Student-Id` (в песочнице `400 student_required`); неверный старый — `400 invalid_old_password`; токен чужого ученика — `403 foreign_account` |
| `POST /api/auth/reset` | Вернуть пароль `support123` и отозвать всё (нужен `X-Student-Id`) |
| `GET /api/admin/users` | Только для роли `admin` — у учётки `agent` всегда `403 insufficient_role` (`details.required_role`, `details.your_role`) |
| `GET /api/journal` | Фаза 2: журнал ученика (по cookie) за 30 минут: `{student_code, items}` |
| `GET /api/journal/stream` | Фаза 2: SSE журнала ученика, событие `request` |
| `POST /api/tasks/{code}/complete` | Фазы 1–2: фронт сообщает, что задание выполнено (фаза 1 — всем онлайн в комнате, фаза 2 — только себе) |
| `POST /api/tasks/{code}/external` | Фаза 3: `{"raw": "<ответ из Postman>"}` |
| `GET /api/progress` | `{chapter_id: {task_id: passed}}` |
| `GET /api/room`, `POST /api/me` | Текущая комната и участники онлайн; задать своё имя `{"name": "Аня"}` |
| `GET /join/{code}`, `POST /rooms/leave` | Войти в комнату по приглашению; вернуться в свою |
| `WS /ws/rooms/{code}` | Совместная работа в комнате (протокол — в `app/services/room_hub.py`) |

Все ошибки возвращаются в одном формате: `{"error": "code", "message": "...", "details": {...}}`.
Интерактивная документация: `/docs`.

Секреты в заголовках (`services/snapshot.py`): в ответе echo `Authorization`,
`X-API-Key`, `Cookie` заменяются на `***` (как советует раздел 2.5 главы 2). В журнале
ученика (и в БД) `Cookie` — `***`, а `Authorization` и `X-API-Key` — частично: видно
схему, начало и конец (`Bearer tok_3f…9a`, ключ `key_12…c4`), пароль Basic — `Basic ***`.
Так ученик видит, что токен ушёл тот и со словом `Bearer`, а полного секрета нет.

**Авторизация (глава 4, `app/api/auth.py`, `services/auth_tokens.py`).** У каждого
ученика (`X-Student-Id`) своя учётка `agent`, свой пароль, токены и ключи (таблица
`auth_token`, пароль после смены — `User.auth_password_hash`); без кода — общая
песочница с паролем по умолчанию. Токены — непрозрачные строки `tok_…`, ключи — `key_…`
(JWT — в отдельной главе). Причина `401` — в поле `error`: `missing_credentials`
(нет пропуска; если токен или ключ в query — сообщение об этом и `details.query_param`),
`malformed_authorization` (нет `Bearer`, двоеточие, кавычки, неизвестная схема, не base64),
`invalid_token` (нет такого, обрезан, ключ вместо токена и наоборот), `token_expired`,
`token_revoked`, `invalid_credentials`. У `401` заголовок `WWW-Authenticate: Bearer
realm="trainer"` (для токена — с `error="invalid_token"`). Время в тестах подменяют
через `auth_tokens.now`.

**`X-Request-ID`.** Каждый ответ `/api/*` (и ошибки тоже) несёт заголовок
`X-Request-ID`: uuid4 или номер, присланный клиентом в том же заголовке (если он из
букв, цифр и `._:-`, до 128 символов). Он же пишется в JSON-лог запроса — по нему
поддержка находит запрос в логах.

**Личный код ученика (`X-Student-Id`).** У каждого пользователя сайта есть
`User.student_code` — 6 символов без похожих (`0/O`, `1/I/L`), уникальный; выдаётся
при создании пользователя (старым — миграцией), виден в `GET /api/room` → `me.student_code`.
Из настоящего Postman его передают заголовком `X-Student-Id` (регистр не важен).
По нему:
- **тикеты свои у каждого ученика** (`Ticket.owner`). При первом обращении с кодом
  ученику создаётся фиксированный набор из 23 тикетов (`services/ticket_seed.py`):
  при `limit=10` «SMS code not received» — на 2-й странице, есть закрытые; названия и описания на английском для обоих языков. Удалить можно
  всё — набор сам не вернётся, только через `POST /api/tickets/reset`. Чужие тикеты
  отвечают 404. Без заголовка или с неизвестным кодом — общая «песочница»
  (`owner = NULL`). `make reset-progress` тикеты не трогает;
- **лимит `/api/limited`** считается на ученика.

**409 на закрытый тикет.** `PUT`/`PATCH` тикета со `status: closed` → `409 ticket_closed`
(«сначала откройте его»). Открыть можно `PATCH {"status": "open"}` (другие поля в том
же запросе допустимы); удалить закрытый можно. Неверное тело — `422` раньше `409`.

## Как добавить главу

Какие главы и в каком порядке делать, — в плане курса
[`content_source/COURSE_PLAN.md`](content_source/COURSE_PLAN.md).

Создайте `app/content/chapters/chNN.yaml` (главы 3–7 уже есть как анонсы — их
дополняют теми же полями):

```yaml
id: ch03
title: "Авторизация и токены"
order: 3
phase: 1                  # 1 — эмулятор, 2 — свой Postman → учебный API, 3 — внешние API
estimated_minutes: 60
goal: |
  Зачем эта глава.
after_completion: |
  Что человек будет уметь.
checklist:
  - "Пункт чек-листа"
quiz:
  - id: q1
    question: "Текст вопроса (можно с `кодом`)"
    options: {A: "…", B: "…", C: "…", D: "…"}
    answer: B
    explanation: "Почему так."
content_md: |
  ## 2.1. Заголовок раздела
  Обычный Markdown: таблицы, блоки кода, цитаты.
```

Глава без заданий и теста (анонс) показывается на главной с пометкой «Глава готовится»,
а на её странице нет блока «Задания» и счётчика заданий.

Контент загружается в БД при старте приложения. `make dev` перезапускается сам при
правке любых `.yaml`, `.json` и `.py` в `app/`. Если приложение запущено иначе,
выполните `make content-sync` (`python -m app.cli sync-content`): команда проверит
YAML и обновит главы и задания в базе без перезапуска, останется обновить страницу.

Синхронизация зеркальная: глава или задание, которых больше нет в YAML, удаляются
из базы. Попытки учеников при этом сохраняются, и если задание вернуть с тем же
`id`, прогресс по нему восстановится. Поэтому `id` задания не меняйте: при
переименовании старое удалится, а прогресс на новый `id` не перейдёт.

Сбросить прогресс всех учеников — `make reset-progress`
(`python -m app.cli reset-progress`). Команда удаляет все попытки (задания и тесты
глав), а пользователи, имена и комнаты остаются. Перед удалением спрашивает
подтверждение; без вопроса — `make reset-progress YES=1`. Отметки чек-листа хранятся
в `localStorage` браузера, их команда не трогает.

## Как добавить задание

Файл `app/content/tasks/ch03.yaml`, где `chapter_id` — id главы:

```yaml
chapter_id: ch03
tasks:
  - id: ch03-task1          # уникальный
    order: 1
    title: "Название"
    description_md: |
      Условие в Markdown.
    expected:               # каким должен быть ответ сервера
      response:
        - {path: status, equals: 200, hint: "Проверь адрес: /api/echo"}
        - {path: body.method, equals: POST, hint: "Нужен POST"}
        - {path: body.args.source, equals: postman, hint: "Добавь ?source=postman"}
        - {path: body.headers.content-type, contains: application/json, hint: "Нужен Content-Type"}
        - {path: body.json.title, exists: true, hint: "В теле нет title"}
        - {path: body.json.priority, in: [low, medium, high], hint: "priority — low/medium/high"}
```

**Утверждения.** `path` начинается с `status`, `headers` (заголовки ответа) или `body`;
дальше ключи через точку. Ответ echo выглядит так: `body.method`, `body.path`,
`body.args.*`, `body.headers.*` (названия в нижнем регистре), `body.json.*`, `body.data`.
У каждого утверждения ровно один оператор:

- `equals` — строгое равенство: `"123"` ≠ `123`;
- `contains` — подстрока или элемент списка; объект — в списке есть элемент с этими
  полями: `{path: body.items, contains: {title: "SMS code not received"}}`;
- `exists: true|false` — `null` считается отсутствием;
- `in: [...]` — одно из значений.

`hint` показывается, если это утверждение — первое несовпавшее. Если `hint` не задан, подсказка формируется автоматически.
Порядок утверждений важен: сначала общее (статус, метод), потом детали.

**Несколько ответов:**

- `steps: [[...], [...]]` — каждый шаг — список утверждений. Без `ordered` шаги можно выполнить в любом порядке (например, «получи 200, 404 и 500»).
- `ordered: true` — шаги строго по порядку (например, «сначала получи 400, потом исправь и получи 200»).
- Новые задания так не пишем: одно задание — один запрос и одна проверка `response`, сценарий из нескольких шагов — несколько заданий подряд (AGENTS.md). `steps`/`ordered` остались у старых заданий глав 1–2.
- `require_console: true` + `console_hint` — после правильного ответа нужно открыть Console (кнопка в нижней строке мини-Postman).

**Фаза 2** (`phase: 2` у задания, запросы из своего Postman) проверяется так же — по
ответам (`response` / `steps` / `ordered`; `require_console` нельзя). Дополнительно
можно задать `request` — эталон **запроса** для подсказок в журнале (`validator.py`):
`method`, `path` (можно `/api/tickets/{{id}}`), `query`, `headers`, `body.json_schema`;
тексты подсказок — встроенные или из `hints` задания (подстановка `{{param}}`). Задавайте
`request` только заданиям из одного запроса: подготовительные запросы (найти `id`)
при том же выбранном задании иначе получат лишние подсказки. Эталоны и типичные ошибки фазы 2 —
`PHASE2_SOLUTIONS` / `PHASE2_MISTAKES` в `tests/test_content_solutions.py` (`{id:<название>}`
в адресе — id тикета ученика; `"untracked": True` — подготовительный запрос до выбора
задания).

После правки проверьте контент: `python -m app.cli check-content`.

## Совместная работа (комнаты)

У каждого пользователя есть своя комната. Кнопка **«Пригласить»** в шапке даёт ссылку
вида `https://сайт/join/<код>`, и все, кто открыл её, оказываются в одной комнате.
**«Выйти»** возвращает в свою комнату. При первом входе сайт спрашивает имя, сменить его
можно кликом по своему аватару.

Участники комнаты видят друг у друга:

- **курсоры** с именем и цветом участника;
- **клики** — «круги» в месте нажатия;
- **выделение текста** на странице, а также выделение и каретку в полях ввода
  (адрес, Params, Headers, Body);
- **общий мини-Postman**: вкладки запросов, метод, адрес, параметры, заголовки, тело,
  открытая вкладка, нажатие Send, ответ, Console (журнал и открыта ли панель) и
  выбранное задание.

Задание, решённое в комнате в мини-Postman (фаза 1), засчитывается **всем, кто в этот
момент онлайн в комнате**. В главах фазы 2 у каждого свой настоящий Postman: журнал,
выбор задания и засчитывание личные.
Тест главы и чек-лист у каждого свои.

**Как устроено.** Браузер подключается по WebSocket к `/ws/rooms/<код>`
(`app/api/rooms.py`, хаб — `app/services/room_hub.py`, фронт — `static/js/collab.js`).
Позиция курсора, клика и выделения передаётся не в пикселях, а относительно элемента
страницы: путь от `<body>` по индексам дочерних элементов плюс доля ширины и высоты
элемента. Поэтому курсор попадает в то же место при разной ширине окна и разном языке
интерфейса. Каждый участник прокручивает колонку мини-Postman сам: курсор и выделение,
ушедшие за край прокручиваемого блока (колонка, журнал Console), не рисуются. Важно для авторов шаблонов: структура страницы должна быть одинаковой у всех
участников. Условные блоки, зависящие от пользователя, делайте через `x-show`, а не
через `x-if` или `{% if %}`.

Общее состояние мини-Postman хранится на сервере в памяти, пока в комнате кто-то есть.
Новый участник сразу получает текущее состояние. Если двое правят одно поле
одновременно, побеждает последнее изменение: для учебного тренажёра этого достаточно.

**Ограничения и безопасность:**

- нужен один процесс uvicorn: комнаты живут в памяти, как и SSE. Для нескольких
  процессов хаб нужно перенести на Redis pub/sub;
- код комнаты — 11 случайных символов, подобрать его перебором нельзя. Подключиться
  к WebSocket можно только с cookie участника комнаты и только со своего сайта (проверка
  `Origin`);
- сообщения ограничены по размеру (256 КБ) и частоте (около 60 в секунду на подключение);
  сервер принимает только известные типы сообщений и поля.

**Прокси.** Caddy проксирует WebSocket без дополнительной настройки. Для nginx нужно:

```nginx
location /ws/ {
    proxy_pass http://127.0.0.1:8000;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_set_header Host $host;
    proxy_read_timeout 1h;
}
```

## Языки (русский и английский)

Язык по умолчанию — английский. Русский включается переключателем EN / RU в шапке
и запоминается в cookie `lang`. Язык браузера сайт не учитывает намеренно. От языка
зависят интерфейс, контент глав, подсказки проверки и тексты ошибок API в поле
`message`. Коды ошибок (`error`) не переводятся: на них опираются программы.

Внутри проекта исходный язык — русский (`SOURCE_LANG` в `app/i18n.py`): на нём
написаны основные файлы контента и строки-ключи каталога. Язык по умолчанию для
пользователя задаёт `DEFAULT_LANG`. Это разные настройки: чтобы сменить язык
по умолчанию, достаточно поменять `DEFAULT_LANG`.

**Перевод контента** лежит рядом с оригиналом, с суффиксом языка:

```
app/content/chapters/ch01.yaml      ← оригинал (русский)
app/content/chapters/ch01.en.yaml   ← перевод
app/content/tasks/ch01.yaml
app/content/tasks/ch01.en.yaml
```

Перевод — полный файл того же формата. Загрузчик проверяет, что он совпадает с
оригиналом во всём, что влияет на прохождение: те же `order`, `phase`, id и порядок
заданий, тот же `expected` (отличаются только тексты `hint` и `console_hint`), те же
вопросы теста с теми же вариантами и ответами и столько же пунктов чек-листа.
Поменяли проверку в оригинале — поменяйте её и в переводе, иначе
`python -m app.cli check-content` и запуск приложения сообщат об ошибке. Если
перевода главы нет, она показывается в оригинале (на русском).

**Строки интерфейса.** В шаблонах, JS и Python строки пишутся по-русски и служат ключами
каталога `app/locales/en.json`:

- шаблоны — `{{ _("Текст") }}` или `{{ _("Глава {n}", n=chapter.order) }}`;
- JS и Alpine-выражения — `t("Текст")`;
- Python — `ApiError(..., "Текст {id}", params={"id": ...})` или `N_("Текст")`.

Какие строки ещё не переведены, показывает `make i18n-missing`
(`python -m app.i18n_extract --missing en`). Тест `tests/test_i18n.py` падает, если в
каталоге не хватает перевода, если в нём остался неиспользуемый ключ или если в
переводе потерялся `{параметр}`.

**Новый язык** (например, `de`): добавьте код в `LANGUAGES` в `app/i18n.py`, создайте
`app/locales/de.json` и файлы `*.de.yaml`.

## Развёртывание на Render

В репозитории есть `render.yaml` (Blueprint): веб-сервис из `Dockerfile`, база —
файл SQLite в `/srv/data/trainer.db`.

1. Запушьте репозиторий на GitHub или GitLab.
2. Render → **New → Blueprint** → выберите репозиторий → **Apply**. Если сервис уже
   создан через New → Web Service, Blueprint не нужен: настройки ниже подходят и ему.
3. Через несколько минут сайт будет доступен на `https://<имя>.onrender.com`.

**Важно про данные.** На бесплатном плане файловая система Render временная: файл базы
(прогресс, комнаты, имена участников) удаляется при каждом деплое, перезапуске и
засыпании сервиса, а засыпает он через 15 минут без запросов. Тренажёр нужен примерно
на месяц, поэтому это осознанно принято: бесплатного плана хватает. Чтобы прогресс сохранялся, нужен постоянный диск, он есть только на платных
планах:

- в `render.yaml` раскомментируйте `plan: starter`, блок `disk` (`mountPath: /srv/data`)
  и переменную `TRAINER_PERSISTENT_DISK=true`;
- или в Dashboard: сервис → **Disks** → **Add Disk**, Mount Path `/srv/data`; затем
  **Environment** → `TRAINER_PERSISTENT_DISK=true`.

Без диска приложение при старте пишет в лог предупреждение о временной базе.

Что уже учтено:

- **Адреса в заданиях.** Render принимает HTTPS и передаёт приложению обычный HTTP с
  заголовком `X-Forwarded-Proto: https`. Скрипт запуска (`docker/start.sh`) запускает
  uvicorn с `--proxy-headers --forwarded-allow-ips='*'`, поэтому приложение видит
  `https://` и подставляет в задания `https://<имя>.onrender.com/api/echo`. Без этих
  флагов в заданиях оказался бы `http://…`, и мини-Postman на HTTPS-странице такой адрес
  бы не отправил.
- **Порт.** Приложение слушает `$PORT`, который задаёт Render (10000).
- **Права на диск.** Диски монтируются с владельцем root. Скрипт запуска выдаёт папку
  с базой пользователю `trainer` и только потом запускает приложение без прав root.
- **WebSocket** (комнаты) работает на Render без настройки. Проверка `Origin` пропускает
  только свой домен.
- **Один процесс.** SQLite, комнаты и rate limit рассчитаны на один экземпляр сервиса,
  как и есть на Render. Не включайте несколько экземпляров (scaling).

После первого деплоя откройте главу 1 и убедитесь, что в задании 1 адрес начинается с
`https://` и с вашего домена.

**Резервная копия базы** (на сервисе с диском, Render → **Shell**):

```bash
python -c "import sqlite3; s=sqlite3.connect('/srv/data/trainer.db'); s.backup(sqlite3.connect('/srv/data/backup.db'))"
```

## Развёртывание на VPS

1. Установите Docker и плагин compose (Ubuntu: `curl -fsSL https://get.docker.com | sh`).
2. Склонируйте репозиторий и создайте `.env`:
   ```
   TRAINER_PUBLIC_BASE_URL=https://trainer.example.com
   TRAINER_CORS_ORIGINS=["https://trainer.example.com","*"]
   TRAINER_COOKIE_SECURE=true
   TRAINER_PERSISTENT_DISK=true
   ```
3. `docker compose up -d --build`. База лежит в томе `trainer-data`; копия:
   `docker compose exec app python -c "import sqlite3; sqlite3.connect('/srv/data/trainer.db').backup(sqlite3.connect('/srv/data/backup.db'))"`.
4. Поставьте перед приложением nginx или Caddy с HTTPS. Пример для Caddy:
   ```
   trainer.example.com {
       reverse_proxy 127.0.0.1:8000 {
           flush_interval -1     # нужно для SSE
       }
   }
   ```
   В `docker-compose.yml` замените `"8000:8000"` на `"127.0.0.1:8000:8000"`, чтобы приложение
   было доступно только через прокси.
5. Обновление: `git pull && docker compose up -d --build`. Миграции применятся сами.

**Что важно знать:**

- Rate limit (60/мин на IP), SSE-брокер и комнаты хранят состояние в памяти процесса.
  Запускайте один воркер uvicorn. Если понадобится масштабирование, перенесите их в Redis.
- После изменения моделей создайте миграцию:
  `alembic revision --autogenerate -m "..."`.
