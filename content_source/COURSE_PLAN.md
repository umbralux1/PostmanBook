# План курса: HTTP + Postman для технической поддержки

Сводный план курса: по нему строим сайт и контент. Детали каждой главы (теория и YAML
заданий) пишутся отдельно, по мере готовности. Главы 1–2 уже на сайте, их описание
ниже соответствует `app/content/`. Главы 3–7 на сайте — анонсы (цель, время, темы)
без теории и заданий.

---

## Общие параметры

- **Аудитория:** специалист технической поддержки без технического бэкграунда.
- **Цель:** научиться диагностировать API-проблемы через Postman и писать понятные
  ответы пользователям.
- **Объём:** 7 глав, ~8–9 часов, 2–3 недели при занятиях 3–4 раза в неделю.
  Тренажёр нужен примерно на месяц, поэтому главы идут по приоритету (см. «Порядок работы»).
- **Формат:** минимум теории → сразу практика → мини-тикет в конце каждой главы.

### Правила проверки (общие для всех глав)

- Задание засчитывается только по запросу и ответу сервера: статус, тело, заголовки,
  последовательность запросов. Вопросы с вариантами в заданиях и проверку
  свободного текста не используем.
- Навык «объяснить пользователю простыми словами» тренируем в теории, чек-листе и
  тесте главы, а не в заданиях.
- Учебный API детерминирован: верный запрос даёт верный ответ.

---

## Три фазы

| Фаза | Главы | Инструмент | Куда шлём запросы | Как проверяем |
|------|-------|-----------|-------------------|---------------|
| **1. Песочница** | 1–2 | Встроенный мини-Postman | Учебный API | На фронте, по `expected` задания |
| **2. Настоящий Postman** | 3–5 | Свой Postman пользователя | Учебный API + заголовок `X-Task-Code` | На сервере, по логу запросов (`services/validator.py`) |
| **3. Самостоятельно** | 6–7 | Свой Postman | Учебный API + внешние (`postman-echo.com`, `httpbin.org`) | Вставка ответа в форму (`/api/tasks/{code}/external`), проверка по структуре ответа |

Переход между фазами — отдельный экран: как установить Postman, как добавить
`X-Task-Code`, первое «проверочное» задание. Бэкенд фаз 2–3 есть, интерфейса нет —
его делаем вместе с главой 3.

Ограничение фазы 1: мини-Postman отправляет запросы через `fetch()` из браузера,
поэтому GET с телом в нём невозможен (браузер не даёт, мини-Postman тоже запрещает).

## Структура глав

### Фаза 1. Песочница (готово)

**Глава 1. Первый запрос: HTTP, URL и мини-Postman** ✅
- Время: ~35 мин. Заданий: 5. Тест: 3 вопроса.
- Темы: зачем поддержке API и Postman, четыре части запроса, анатомия URL
  (протокол, хост, путь, query), GET vs POST, query vs тело, мини-Postman и echo.
- Главный навык: собрать GET с query-параметрами и найти их в ответе.
- Мини-тикет: фильтр не работает (опечатка `stauts` в параметре).

**Глава 2. Ответ сервера: статус-коды, JSON и заголовки** ✅
- Время: ~55 мин. Заданий: 9. Тест: 5 вопросов.
- Темы: три части ответа, группы кодов и 200/201/400/401/403/404/500/503, JSON за
  5 минут и типы значений, `Content-Type`, `Accept`, `Authorization`, Console,
  безопасность (токены, production).
- Главный навык: отправить POST с JSON, прочитать ответ, найти ошибку в JSON.
- Мини-тикеты: невалидный JSON (`high` без кавычек → 400), две ошибки в JSON.

### Фаза 2. Настоящий Postman

**Глава 3. Методы HTTP и статус-коды в диагностике** ✅ (план и решения — `CH03_PLAN.md`)
- Время: ~100 мин. Заданий: 9.
- Темы: переход в настоящий Postman и `X-Task-Code`; GET/POST/PUT/PATCH/DELETE на
  `/api/tickets`; идемпотентность; коды 201, 204, 409, 422, 429, 502, 503; правило
  «`4xx` — разбираемся сами, `5xx` — эскалируем»; `X-Request-ID`; пагинация
  (`page`, `limit`, сколько всего записей); rate limit (`429` и заголовок `Retry-After`).
- Главный навык: по коду и телу ошибки понять, кто виноват.
- Задания про пагинацию и rate limit:
  - тикет «клиент не видит свой тикет в списке» — тикет на второй странице,
    найти его через `page`/`limit`;
  - получить `429`, найти в ответе `Retry-After` и повторить запрос после паузы.
- Мини-тикет: `PUT` без обязательного поля → `422`, найти поле по телу ошибки.
- API: CRUD `tickets` есть (DELETE → 204). Добавить: 409 (конфликт, например
  повторное создание), 422 с понятным телом ошибки, `X-Request-ID` во всех ответах,
  пагинацию `GET /api/tickets?page=&limit=` (в ответе — `total` и номер страницы),
  учебный эндпоинт с лимитом запросов: `429` + `Retry-After`, лимит считается
  отдельно на каждого ученика.

**Глава 4. Авторизация и токены** — приоритет 2
- Время: ~75 мин. Заданий: 6.
- Темы: заголовок `Authorization`, Bearer / API Key / Basic, вкладка Authorization
  в Postman, `401` vs `403`, просроченный и отозванный токен, токены в тикетах.
- Главный навык: отличить `401` от `403` и объяснить разницу.
- Мини-тикет: «после смены пароля всё отвечает 401» — старый токен, получить новый.
  (Тикет «скриншот с токеном» — в теорию и тест: проверить по запросу нечем.)
- API: эндпоинты под Bearer, API Key и Basic; выдача токена; просроченный и
  отозванный токены; ресурс, доступный только админу (403).

**Глава 5. Окружения и коллекции** — приоритет 4, можно сократить до теории
- Время: ~60 мин. Заданий: 5.
- Темы: Environment, `{{base_url}}` и `{{token}}`, переключение staging/production,
  типовые ошибки с `{{}}`; Collection и папки, импорт curl, экспорт коллегам.
- Главный навык: переключать среды без ручной правки адресов.
- Мини-тикет: `404` только на staging.
- Проверка: сервер видит только сам запрос, а не окружение или коллекцию. Поэтому
  задания вида «отправь на staging, потом на production одним запросом с переменной»
  и «запрос из импортированного curl пришёл правильным».
- API: две «среды» учебного API (например, `/api/staging/...` и `/api/...`)
  с различием, которое даёт 404 на staging.

### Фаза 3. Самостоятельно

**Глава 6. Отладка: Console и типовые ошибки** — приоритет 5
- Время: ~75 мин. Заданий: 5.
- Темы: Console в настоящем Postman, таймаут, редирект, пустой ответ, чтение тела
  ошибки, сравнение «работающего» и «сломанного» запросов, что собрать для эскалации.
- Главный навык: найти причину по Console, а не гадать.
- Мини-тикет: `200` без тела.
- Внешние API: httpbin `/delay`, `/redirect`, `/status`. SSL-ошибки — только
  теорией (нужны сторонние хосты вроде badssl.com). Учитывать, что внешние сервисы
  бывают недоступны: в задании держать запасной адрес на учебном API.

**Глава 7. Финальные кейсы: полный цикл поддержки** — приоритет 3
- Время: ~90–120 мин. Кейсов: 5.
- Темы: от тикета к воспроизведению, когда решать самому и когда эскалировать, что
  приложить к эскалации, как объяснить причину простыми словами (теория и тест).
- Главный навык: пройти цикл «тикет → воспроизвести → найти причину → проверить решение».
- Кейсы (каждый проверяется по запросам: сначала воспроизвести ошибку, потом получить
  верный ответ или нужные данные):
  1. `400` из-за JSON;
  2. `401` после смены пароля;
  3. `403` из-за прав;
  4. `404` только на staging (если есть гл. 5, иначе — опечатка в пути);
  5. `500` с `request_id` — найти `X-Request-ID` в ответе и передать его в
     запросе-«эскалации».
- Зависит от API глав 3–4 (и 5 для кейса 4).

## Формат каждой главы на сайте

1. **Цель главы** — 1–2 предложения (`goal`).
2. **Зачем это в поддержке** — реальный пример тикета.
3. **Теория** — коротко, с визуалом (`content_md`).
4. **«Как это выглядит в Postman»** — скриншот или схема.
5. **Задания** — 5–9 штук, с автопроверкой и подсказками; у каждого задания фазы 1 —
   эталонное решение и типичные ошибки в `tests/test_content_solutions.py`.
6. **Чек-лист** — что запомнить.
7. **Тест главы** — 3–5 вопросов с вариантами.
8. **Кнопка «Дальше»**.

Каждая глава — на русском (`chNN.yaml`) и английском (`chNN.en.yaml`).
