## Что мешает сделать главу сразу (найдено в коде)

1. **`X-Task-Code` общий для всех.** Код = id задания (`ch03-task1`). Запрос любого
   ученика попадает на страницу ожидания у всех, кто её открыл; сервер не знает,
   *чей* это запрос, и задание никому не засчитывается (`recorder.record` пишет
   `ReceivedRequest`, но не `Attempt`).
2. **Проверка фазы 2 смотрит только на запрос** (`validator.py`: method, path, query,
   headers, body). Задания главы требуют проверять **ответ** (409, 204, 429,
   `Retry-After`, тикет на второй странице) и **последовательность** (удалил → 404;
   429 → пауза → 200). Ответ сервер сейчас не записывает.
3. **Тикеты общие на всех** (`Ticket` без владельца). Ученики видят и портят чужие
   тикеты; задание «тикет на второй странице» недетерминировано.
4. **Интерфейса фазы 2 нет**: `phases/phase2_wait.html` — заготовка, страница главы
   рассчитана на мини-Postman.
5. **Нет API**: пагинации (`page`, `total`), 409, `X-Request-ID`, лимита на ученика
   (`slowapi` считает по IP и только для служебных эндпоинтов).

## Предлагаемые решения

### 1. Два заголовка: ученик и задание (решение владельца)

- `X-Student-Id: K7M2QX` — личный id ученика: короткий код (6 символов), новое поле
  `User.student_code` (миграция, уникальное). Показан на странице главы фазы 2 с
  кнопкой «Скопировать».
- `X-Task-Code: ch03-task4` — id задания, как сейчас; копируется с карточки задания.
- Задание решается только запросами с **обоими** заголовками. Запрос без одного из
  них (или с неизвестным `X-Student-Id`) учебный API обрабатывает как обычно, но
  никуда не засчитывает; если есть только один из заголовков — в журнале ученика
  (когда известен `X-Student-Id`) подсказка «не хватает заголовка X-Task-Code».
- Тикеты, лимит запросов и журнал привязаны к `X-Student-Id`, поэтому он нужен и в
  запросах, которые готовят задание (например, найти id тикета).

### 2. Проверка фазы 2 — тем же `checker.js`, по ответу (как в фазе 1)

- Middleware: для запросов с `X-Student-Id` + `X-Task-Code` записывает в
  `ReceivedRequest` ещё и **ответ** (статус, заголовки, тело; поля `response_status`,
  `response_headers`, `response_body`, `student_code` — миграция).
- SSE-канал — на ученика (`/api/tasks/{id}/stream` отдаёт только запросы с его
  `X-Student-Id`; id берём из cookie-пользователя, а не из URL).
- Страница главы получает запросы с ответами и прогоняет их через **тот же
  `checker.js`** и тот же формат `expected` (`response` / `steps` / `ordered`). При
  успехе — `POST /api/tasks/{id}/complete` (разрешить phase 2).
- При открытии страницы подтягиваются последние запросы ученика (`/last` → список за
  ~30 мин), чтобы задание засчиталось, даже если запрос отправлен до открытия вкладки.
- Плюсы: одна логика проверки на обе фазы, эталоны и ошибки в
  `tests/test_content_solutions.py` работают так же (через настоящий сервер + Node).
- `validator.py` (проверка запроса) остаётся для подсказок «что не так в запросе»
  (неверный метод/путь/заголовок) — показываем рядом с результатом checker.js.
- **Меняет решение из AGENTS.md** («сервер фазу 1 не проверяет, `validator.py` — для
  фазы 2»): нужно согласие владельца.

### 3. Тикеты — свои у каждого ученика

- `Ticket.owner` = код ученика (миграция, индекс). Запросы без кода — в общей
  «песочнице» `owner = NULL` (как сейчас).
- При первом обращении с кодом ученику создаётся набор из ~23 тикетов (фиксированные
  названия и статусы из YAML/кода), чтобы пагинация была детерминированной.
- Сброс своих тикетов: `POST /api/tickets/reset` (с кодом) — упоминается в подсказках.
- `make reset-progress` тикеты не трогает (или трогает — решить).

### 4. Доработки учебного API

| Что | Как |
|-----|-----|
| `X-Request-ID` | middleware на всех ответах `/api/*` (uuid4; если клиент прислал свой — вернуть его) |
| Пагинация | `GET /api/tickets?page=&limit=` → `{items, page, limit, total, pages}`; `count` оставить для совместимости |
| `409` | `PATCH`/`PUT` закрытого тикета (`status: closed`) → `409 ticket_closed` с телом «сначала откройте тикет» |
| `422` | есть; проверить, что тело понятное: `details.missing`, `details.invalid` |
| `204` | есть (`DELETE`) |
| `429` | `GET /api/limited` (или `/api/tickets/export`): 3 запроса за 10 с на ученика → `429` + `Retry-After: N` + тело с объяснением |
| `502`/`503` | `/api/status/{code}` уже есть; в тело 5xx добавить `request_id` |

Все тексты ошибок — через `ApiError` / `N_` + `en.json`.

### 5. Интерфейс фазы 2: без мини-Postman (решение владельца)

- В заданиях, где используется настоящий Postman, **нет никакой эмуляции Postman**:
  на странице главы фазы 2 мини-Postman не подключается (ни builder, ни вкладки,
  ни кнопки Send/Console), и на сайте нельзя собрать или отправить запрос.
- Вместо него — панель **«Твой Postman»** только для чтения: оба заголовка для
  текущего задания (копировать), живой журнал полученных сервером запросов (метод,
  путь, статус, раскрываемый ответ), результат проверки и подсказки. Карточки заданий
  и автопереход (`task_order.js`) — как в фазе 1.
- Проверить в тесте страницы: у главы фазы 2 в HTML нет `#builder` и скриптов
  мини-Postman.
- **Экран перехода** = раздел 3.1 теории + задание 1 «Проверка связи»: как установить
  Postman (desktop; web-версия не достучится до `localhost` — только к Render),
  как добавить заголовок, как отправить первый запрос.
- Комнаты: в фазе 2 у каждого свой Postman; журнал и засчитывание — личные (решение
  владельца), комната показывает только присутствие.
- DOM одинаковый у всех участников комнаты (правило из AGENTS.md) — личные данные
  через `x-text`/`x-show`.

## Контент главы

Время ~100 мин. Файлы: `app/content/chapters/ch03(.en).yaml`,
`app/content/tasks/ch03(.en).yaml`.

### Теория (`content_md`)

1. **3.1 Переходим в настоящий Postman** — установка, где Method/URL/Headers/Body
   (то же, что в мини-Postman), заголовок `X-Task-Code`, личный код.
2. **3.2 Методы на примере тикетов** — таблица GET/POST/PUT/PATCH/DELETE → что делает
   с `/api/tickets`; PUT заменяет целиком, PATCH — частично.
3. **3.3 Идемпотентность** — что безопасно повторить (GET, PUT, DELETE) и что нет
   (POST → дубль). Пример тикета «клиент нажал дважды — две заявки».
4. **3.4 Коды в диагностике** — 201, 204, 409, 422, 429, 502, 503 (повтор 4xx/5xx из
   гл. 2 — коротко). Правило «`4xx` — разбираемся сами, `5xx` — эскалируем» и
   исключения (429 — подождать; 409 — состояние данных).
5. **3.5 `X-Request-ID`** — где найти в Postman (вкладка Headers ответа), зачем
   прикладывать к эскалации.
6. **3.6 Пагинация** — `page`, `limit`, `total`, `pages`; «не вижу в списке» ≠ «нет».
7. **3.7 Rate limit** — `429`, `Retry-After`, что сказать клиенту.

Плюс: словарик, чек-лист, тест главы (5 вопросов: идемпотентность, PUT vs PATCH,
кто виноват при 422 / 502, что значит `Retry-After`, что приложить к эскалации).

### Задания (13)

Атомарные (решение владельца, AGENTS.md): одно задание — один запрос и одна проверка
ответа. Многошаговые 5, 8, 9 разбиты на пары (2026-11-10), `id` перенумерованы по
порядку: номер на сайте = код `X-Task-Code`.

| # | Название | Что сделать | Проверка (`expected.response`) |
|---|----------|-------------|--------------------------------|
| 1 | Проверка связи | `GET /api/echo` из Postman с `X-Student-Id` и `X-Task-Code` | `status 200`, `body.method GET` |
| 2 | Список тикетов | `GET /api/tickets` | `200`, есть `items`, `total` |
| 3 | Создать тикет | `POST /api/tickets` с JSON | `201`, `body.id` есть, заголовок `x-request-id` есть |
| 4 | PATCH vs PUT | взять в работу: `PATCH {status: in_progress}` | `200`, `body.status = in_progress`, `title` не изменился |
| 5 | Удалить тикет | `DELETE` тикета из задания 3 | `204` |
| 6 | Проверить, что удалён | `GET` того же адреса | `404`, `body.error = not_found` |
| 7 | Конфликт | изменить закрытый тикет → `409`, прочитать причину | `409`, `body.error = ticket_closed` |
| 8 | Тикет-«невидимка» | клиент не видит «SMS code not received» — найти на 2-й странице | `200`, `body.page = 2`, в `items` есть нужный `title` |
| 9 | Слишком часто | получить `429`, найти `Retry-After` | `429` + заголовок `retry-after` |
| 10 | Повторить после паузы | подождать `Retry-After`, `GET /api/limited` | `200`, `body.ok = true` |
| 11 | Мини-тикет: 422 — воспроизвести | `PUT` без `priority` | `422`, `details.missing ∋ priority` |
| 12 | Мини-тикет: 422 — исправить | `PUT` с `priority: low` (и увидеть стёртый `description`) | `200`, `title`, `status = in_progress` |
| 13 | Мини-тикет: 503 и эскалация | `GET /api/status/503`, найти `X-Request-ID` (заголовок и `request_id` в теле), составить эскалацию | `503`, `body.request_id` и заголовок `x-request-id` есть |

Цена атомарности: 6 засчитается на любом `404 not_found`, 10 — на любом `200` от
`/api/limited`, даже без предшествующего `DELETE` / `429`.

Каждое — с эталоном и типичными ошибками в `tests/test_content_solutions.py`
(расширить на фазу 2: запросы с `X-Student-Id` и `X-Task-Code`, ответы из
записанного журнала → `checker.js`; типичная ошибка — запрос без одного из заголовков).

## Решено владельцем

- Два заголовка: `X-Student-Id` (ученик) и `X-Task-Code` (задание); задание решается
  только запросами с обоими.
- В заданиях с настоящим Postman мини-Postman (эмуляции) нет.
- Проверка фазы 2 — по ответу через `checker.js` на фронте (решение в AGENTS.md
  обновить при реализации).
- Названия заголовков: `X-Student-Id` и `X-Task-Code`.
- Комнаты в фазе 2: задание засчитывается только тому, кто отправил запрос.
- Тикеты — свои у каждого ученика (по `X-Student-Id`) с готовым набором и сбросом.
- Чего нет в учебном API (409, пагинация, `429`, `X-Request-ID`, тикеты по ученику) —
  создаётся на этапе 1 «API», до контента.

- 409: `PUT`/`PATCH` закрытого тикета → `409 ticket_closed` («тикет закрыт, сначала
  откройте его»). Открыть можно `PATCH {"status": "open"}`.
