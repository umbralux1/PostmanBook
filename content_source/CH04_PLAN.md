# План главы 4: «Авторизация и токены»

Черновик для согласования с владельцем. Основа — раздел «Глава 4» в `COURSE_PLAN.md`.
Формат и инфраструктура — как в главе 3 (`CH03_PLAN.md`): фаза 2, настоящий Postman,
заголовки `X-Student-Id` + `X-Task-Code`, проверка по ответам из журнала через `checker.js`.
После согласования устойчивые решения переносятся в `AGENTS.md` / `README.md`.

## Что уже есть и чего не хватает (найдено в коде)

- Инфраструктура фазы 2 готова: журнал с ответами, SSE, панель «Твой Postman»,
  `checker.js` (`response` / `steps` / `ordered`, `contains` с объектом). Новой
  инфраструктуры проверки глава не требует.
- `401` и `403` есть только как «пустые» коды `/api/status/401`, `/403`. Эндпоинтов,
  которые **проверяют** `Authorization`, нет; токенов, логина, ролей нет.
- В главе 2 уже объяснены `401` / `403` (раздел 2.2, «пропуск») и заголовок
  `Authorization: Bearer …` (2.4). Глава 4 не повторяет, а углубляет: откуда берётся
  токен, почему он перестаёт работать, как отличить причины `401`.
- `services/snapshot.py` уже заменяет `Authorization` (и `Cookie`) на `***` — и в ответе
  echo (на этом построено задание главы 2 про безопасность), и в журнале / БД.
  `X-API-Key` не скрывается. В первой версии плана было ошибочно «как есть» — см.
  открытый вопрос.
- Checker видит только ответ, не запрос. Значит, ответ должен сам говорить, каким
  способом ученик вошёл (поле `auth` в теле) — иначе задание про Basic / API Key не
  проверить.

## Предлагаемые решения

### 1. Учебный API авторизации (`app/api/auth.py`)

Всё — своё у каждого ученика (по `X-Student-Id`, как тикеты). Без `X-Student-Id` —
общая «песочница» (логин и проверка работают, смена пароля — нет, `400`).

Учебная учётка: логин `agent`, пароль `support123`, роль `agent` (сотрудник
поддержки). Админской учётки ученику не даём: `403` — главный урок.

| Эндпоинт | Что делает | Ответы |
|----------|-----------|--------|
| `POST /api/auth/login` `{username, password, expires_in?}` | выдаёт токен | `200 {access_token, token_type: "Bearer", expires_in, role}`; неверные данные → `401 invalid_credentials`; нет полей → `422` |
| `GET /api/auth/me` | «кто я»: принимает Bearer, Basic и `X-API-Key` | `200 {username, role, auth: "bearer"\|"basic"\|"api_key", expires_at}`; ошибки — ниже |
| `POST /api/auth/api-keys` (Bearer) | создаёт API-ключ | `201 {api_key}` |
| `GET /api/admin/users` | ресурс только для роли `admin` | с токеном `agent` → `403 insufficient_role`, `details.required_role: "admin"` |
| `POST /api/auth/change-password` (Bearer) `{old_password, new_password}` | меняет пароль, **отзывает все токены и ключи** ученика | `200`; неверный старый → `400 invalid_old_password` (токен-то верный); токен другого ученика → `403 foreign_account`; песочница → `400 student_required` |
| `POST /api/auth/reset` | вернуть пароль `support123`, отозвать всё | `200` (упоминается в подсказках) |

Ошибки `401` (у всех защищённых эндпоинтов), тело `{error, message, details}` (общий
формат ошибок; `X-Request-ID` — в заголовке) + `WWW-Authenticate: Bearer realm="trainer"`:

| `error` | Когда | Что этим учим |
|---------|-------|---------------|
| `missing_credentials` | нет `Authorization` и `X-API-Key` | «пропуск не предъявлен» |
| `malformed_authorization` | нет слова `Bearer`, `Bearer:` с двоеточием, лишние кавычки, `Basic` не base64 | частая ошибка при ручном вводе |
| `invalid_token` | токена такого нет (опечатка, обрезан при копировании, чужая среда) | |
| `token_expired` | истёк `expires_at` | просроченный токен |
| `token_revoked` | отозван сменой пароля / reset | «после смены пароля всё 401» |

- `expires_in` в логине — учебное удобство: по умолчанию 900 с, можно задать 5–3600 с,
  чтобы в задании про просрочку не ждать 15 минут.
- Токены — непрозрачные строки `tok_…` (32 случайных символа), API-ключи — `key_…`.
  JWT — в следующей главе, целиком про него.
  Хранятся в новой таблице `auth_token` (`token`, `owner`, `kind`, `role`,
  `expires_at`, `revoked_at`); пароль ученика — поле `User.auth_password_hash` (null =
  `support123`). Миграция; внешние ключи с именами. На Render база стирается при
  перезапуске — для токенов это нормально (ученик просто логинится заново).
- API-ключ принимается только в заголовке `X-API-Key`. Ключ в query (`?api_key=`) →
  `401 missing_credentials` с `details.hint` «ключ передают в заголовке: адрес попадает
  в логи» (Postman во вкладке Authorization → API Key умеет и так, и так — урок).
- Все тексты ошибок — `ApiError` / `N_` + `en.json`. `X-Request-ID` — уже в middleware.
- Эндпоинты закладываются и под главу 7 (кейсы «401 после смены пароля», «403 из-за прав»).

### 2. Журнал: как показывать `Authorization` (открытый вопрос, этап 2)

Владелец решил «не маскировать», но исходил из ошибки в плане: сейчас в журнале
`authorization: ***` целиком — не видно даже, есть ли слово `Bearer`. Довод за показ:
ученик сравнивает токен из ответа логина с тем, что ушёл (обрезан, лишний пробел,
старый). Echo в любом случае оставляем с `***` (урок главы 2).

### 3. Подсказки в журнале на типичные ошибки

Владелец в главе 3 ошибался «заголовки во вкладке Params» — здесь то же будет с
токеном. `expected.request` + `hints.py`: «токен ушёл в query, а не в Headers /
Authorization», «нет слова Bearer», «старый `X-Task-Code`».

## Контент главы

Время ~75 мин. Файлы: `app/content/chapters/ch04(.en).yaml` (сейчас анонс),
`app/content/tasks/ch04(.en).yaml`.

### Теория (`content_md`)

1. **4.1 Кто ты и что тебе можно** — аутентификация («кто ты», `401`) и авторизация
   («что тебе можно», `403`). Пример тикета: «вчера работало, сегодня 401».
2. **4.2 Три способа предъявить пропуск** — Bearer-токен, Basic (логин:пароль в base64 —
   это **не** шифрование), API Key (`X-API-Key`). Где что встречается.
3. **4.3 Вкладка Authorization в Postman** — Type: Bearer Token / Basic Auth / API Key;
   Postman сам добавляет заголовок (виден в Headers как auto-generated); не дублировать
   вручную. «Inherit auth from parent» — одной строкой, подробно в главе 5.
4. **4.4 Откуда берётся токен** — логин → `access_token`, `expires_in`; токен = временный
   пропуск, пароль = паспорт.
5. **4.5 401 или 403: диагностика** — таблица причин `401` (нет, опечатка в `Bearer`,
   обрезан, просрочен, отозван, токен от другой среды) и `403` (нет роли, не тот
   аккаунт); где смотреть: тело `error`, заголовок `WWW-Authenticate`. Что делать
   поддержке в каждом случае и что сказать клиенту.
6. **4.6 Просроченный и отозванный токен** — смена пароля, «выйти на всех
   устройствах», отзыв ключа; почему после смены пароля старые токены не работают.
7. **4.7 Токены в тикетах** — никогда не просить пароль; токен на скриншоте → попросить
   отозвать / сменить; маскировать в эскалации; не вставлять токены в сторонние сайты
   (декодеры и т. п.); production-токены клиента не использовать; настоящие логи
   маскируют секреты (`Bearer tok_ab…9f`). Мостик к следующей главе: «бывают токены,
   внутри которых данные, — JWT».
   (Тикет «скриншот с токеном» — здесь и в тесте: по запросу не проверить.)

Плюс: словарик (аутентификация, авторизация, токен, Bearer, Basic, API Key, роль,
отзыв, `WWW-Authenticate`), чек-лист, тест главы (5 вопросов: 401 vs 403 по ситуации;
что значит base64 в Basic; клиент прислал скриншот с токеном; почему после смены
пароля 401; что сказать клиенту при 403).

### Задания (12, атомарные)

Правило владельца (2026-11-10): **одно задание — один запрос и одна проверка ответа**
(`expected.response`, без `steps` / `ordered`). Сценарий из нескольких шагов — это
несколько заданий подряд; следующее может использовать результат предыдущего (токен,
ключ). Все — с `X-Student-Id` и `X-Task-Code: ch04-taskN`.

| # | Название | Запрос | Проверка ответа |
|---|----------|--------|-----------------|
| 1 | Без пропуска | `GET /api/auth/me` без авторизации | `401`, `error = missing_credentials`, заголовок `www-authenticate` есть |
| 2 | Получить токен | `POST /api/auth/login` `{username, password}` | `200`, `access_token` есть, `token_type = Bearer` |
| 3 | Войти по токену | `GET /api/auth/me`, Authorization → Bearer Token (токен из задания 2) | `200`, `auth = bearer`, `username = agent` |
| 4 | Basic Auth | `GET /api/auth/me`, Authorization → Basic Auth (`agent` / `support123`) | `200`, `auth = basic` |
| 5 | Создать API-ключ | `POST /api/auth/api-keys` с Bearer | `201`, `api_key` есть |
| 6 | Войти по API-ключу | `GET /api/auth/me`, Authorization → API Key (`X-API-Key`, Add to Header) | `200`, `auth = api_key` |
| 7 | 401 или 403 | `GET /api/admin/users` с Bearer | `403`, `error = insufficient_role`, `details.required_role = admin` |
| 8 | Короткий токен | `POST /api/auth/login` с `"expires_in": 10` | `200`, `expires_in = 10` |
| 9 | Просроченный токен | через 10+ с: `GET /api/auth/me` с токеном из задания 8 | `401`, `error = token_expired` |
| 10 | Смена пароля | `POST /api/auth/change-password` `{old_password, new_password}` | `200`, `changed = true` |
| 11 | Мини-тикет: «после смены пароля всё 401» | `GET /api/auth/me` со старым токеном | `401`, `error = token_revoked` |
| 12 | Мини-тикет: новый токен | `POST /api/auth/login` с новым паролем | `200`, `access_token` есть |

Ограничение: задание 12 по ответу не отличить от логина со старым паролем после
`reset` — проверяется только, что логин успешен. Принимаем: урок — «получить новый токен».

Время ~80 мин (в `COURSE_PLAN.md` было 75 и 6 заданий).

Каждое — с эталоном и типичными ошибками в `tests/test_content_solutions.py`
(`PHASE2_SOLUTIONS` / `PHASE2_MISTAKES`): без слова `Bearer`, токен в Params,
неверный пароль, API-ключ в query, задание 9 без паузы (`200`), запрос без одного из
заголовков.

Риск: задание 10 меняет пароль — повтор заданий 2–8 с `support123` даст `401`.
Подсказка в них: «менял пароль — `POST /api/auth/reset`».
